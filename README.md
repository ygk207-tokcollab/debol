# Debol (Telegram Mini App storefront + admin panel)

Telegram Mini App storefront + admin control panel for an Ethiopian children's clothing, shoe and toy
shop. Cash on delivery only. English only (Amharic was removed; `docs/DATA-AND-MIGRATIONS.md` records
the V3 migration that dropped the `_am` columns). Prices in ETB. `store_settings.store_name_en` seeds as
`Debol` in `V4__store_branding.sql`, and the header/favicon/logo mark come from the Debol artwork in
`public/`.

Everything documented here was read out of the code in this repository. Where something is missing
or only half-wired, it is listed under [Not implemented / deviations](#not-implemented--deviations).

> **What ships in this checkout.** The frontend and the API are a single npm package: the Vite root is
> the repository root (`src/`, not `frontend/src/`), and the server that `npm run dev` / `npm start`
> launches is the Express app in `server.ts` + `server/`. The Kotlin + Spring Boot + Flyway backend
> described throughout most of this document is the production design it mirrors; that source is not in
> this tree. This Express server persists: set **`DATABASE_URL`** (a Neon/Postgres connection string) and
> `server/db.ts` creates the 19-table schema, `server/persist.ts` seeds it from `docs/api-samples/*.json`
> on first boot, loads it back at startup and writes it back after every successful mutation. **With no
> `DATABASE_URL` it is the old in-memory demo** — orders, carts and uploaded images reset on restart. See
> [Connecting a Postgres database](#connecting-a-postgres-database-neon) below.

## What is actually implemented

Storefront (`src/pages/storefront`, API under `/api/v1`):

- Home (`GET /api/v1/store`): store name/tagline/contact, active banners, categories with real product
  counts, featured + newest products, collections.
- Catalog with filters (`GET /api/v1/products`): `category`, `q`, `audience`, `gender`, `size`,
  `minPrice`, `maxPrice`, `inStock`, `featured`, `sort` (default `newest`), `page`, `pageSize` (default 12).
- Product page by slug with variants (size + colour + stock), size guides (`GET /api/v1/size-guides`).
- Guest cart keyed by the `X-Cart-Key` header (`/api/v1/cart/**`), kept as-is across sign-in
  (`POST /api/v1/me/cart/claim` is a no-op: the SPA sends the same key before and after, so there is
  nothing to merge).
- Checkout with delivery-zone fee lookup, quote endpoint (`POST /api/v1/checkout/quote`),
  `expectedTotal` price-change guard, idempotency key replay guard, row-locked stock decrement
  (`POST /api/v1/checkout`). Only `CASH_ON_DELIVERY` is accepted.
- Customer identity: phone sign-in mints a random bearer session (`POST /api/v1/customers/auth/phone`)
  and the phone *is* the credential - anyone who knows a number can open that account, because no SMS
  provider exists to prove ownership. Signing in again reuses that phone's profile and retires its older
  session; signing out kills the presented token but keeps the profile, keyed under an unguessable string.
  `POST /api/v1/telegram/auth` reads the name out of Telegram `initData` but cannot verify the signature
  (no `TELEGRAM_BOT_TOKEN` is configured), so such a session starts with no phone.
- Every `/me/**` screen resolves the bearer token: profile reads and writes the stored customer, saved
  addresses live inside the persisted profile row, and the order list, order detail and cancel request
  only see orders whose `customerPhone` matches the signed-in phone.
- Order tracking by order number + public receipt token (`GET /api/v1/orders/track/{orderNumber}`).

Admin panel (`src/pages/admin` at `/admin/*`, API under `/api/v1/admin`):

- Email + BCrypt(12) login, JWT sessions, role-based authorization
  (`OWNER` / `MANAGER` / `DELIVERY_STAFF`), token version revocation.
- Dashboard counted from PostgreSQL, order search/detail, status transitions, courier assignment,
  cash collection, cancellation with optional stock restore.
- Product list and CRUD, images (URL link + multipart upload), variant stock adjustments,
  inventory movement history, category CRUD, delivery zones, store settings, administrators, audit log,
  notification outbox history + retry + manual dispatch, Telegram status/pairing endpoints.

Telegram integration (`backend/src/main/kotlin/com/kidsstore/telegram`):

- `TelegramBotClient` - thin Bot API client (`sendMessage`, `getUpdates`, `answerCallbackQuery`),
  token read only from `TELEGRAM_BOT_TOKEN`.
- `PollingWorker` - long-polls for admin pairing (`/start 123456`, `/pair 123456`) and inline order
  buttons (`confirm:<id>`, `reject:<id>`, `deliver:<id>`); `/start` without a code sends the welcome
  message with an "Open the store" URL button.
- `OutboxDispatcher` + `OutboxStateService` - transactional outbox (`notification_outbox` table) with
  exponential backoff, `locked_until` claim, `RETRY` and `DEAD_LETTER` states.
- `NotificationService` + `MessageRenderer` - new order, status change, cash collected, cancellation,
  low/out-of-stock and test messages; idempotency keys prevent duplicate sends.

Data layer:

- 26 tables created by Flyway `V1__baseline_schema.sql`; settings rows + sample catalogue from
  `V2__configuration_and_sample_catalog.sql`; `V3__age_groups_and_single_language.sql` adds the
  admin-managed age groups and drops the Amharic columns; `V4__store_branding.sql` renames the shop to
  Debol. Hibernate runs with `ddl-auto: validate`.
- Money is `NUMERIC(12,2)` everywhere, formatted with `BigDecimal` (`com.kidsstore.common.Money`).

## Quickstart

**This checkout (Express mock, no database required).** `server.ts` serves the API and the app from one
port in both modes, so there is nothing to proxy and no PostgreSQL role to create:

```bash
npm install
npm run dev            # tsx server.ts - Vite middleware + HMR, http://127.0.0.1:3000
npm run typecheck      # tsc --noEmit
npm run build          # tsc --noEmit && vite build -> dist/
npm start              # tsx server.ts - same entry point; see the NODE_ENV note below
```

Both scripts are `tsx server.ts`, and `PORT` defaults to 3000 with `HOST` bound to `0.0.0.0`. `server.ts`
only serves the built `dist/` when `NODE_ENV=production`; otherwise it runs the Vite middleware. The
Dockerfile and `render.yaml` both set `NODE_ENV=production`, so containers are correct — to exercise the
same production path locally, prefix the env (e.g. `NODE_ENV=production PORT=3000 npm start`). Running
`npm start` bare gives you dev mode, so build it before serving `dist/` either way.

Point the app at an API on another origin with `VITE_API_BASE_URL=https://host/api/v1 npm run build`;
it defaults to the relative `/api/v1`, which is what same-origin deployments should use.

Sign-in is real even in this mode: set `ADMIN_BOOTSTRAP_PASSWORD` (12+ characters) before starting, and
it is scrypt-hashed at boot onto every active `OWNER` account in
`docs/api-samples/admin_administrators.json` (`owner@kidsstore.test`, `demo@kidsstore.test`). Without that
variable the panel answers `403 password_not_set` rather than accepting an arbitrary password, and
`/admin/auth/dev-login` answers `404` unless `ADMIN_DEV_LOGIN=true` outside production. In memory-only
mode the hash lives in the process, so the same variable has to be set again after each restart, and
uploaded images are held in RAM and disappear on restart (`GET /api/v1/media/images/:id` says so).

## Connecting a Postgres database (Neon)

`DATABASE_URL` is the only switch. With it set, startup goes: `migrate()` -> `isEmpty()` -> seed from
`docs/api-samples` or `hydrate()` -> apply `ADMIN_BOOTSTRAP_PASSWORD`. Afterwards every successful
`POST`/`PUT`/`PATCH`/`DELETE` writes the whole state back inside one transaction
(`server/persist.ts: persistAll`), and tables are upserted then trimmed to the ids still referenced —
never truncated, because truncating a product would cascade and delete its stored image bytes.

1. In Neon, create the project and copy the **pooled** connection string (its host ends in `-pooler`);
   that is what a long-lived server should use. It arrives as
   `postgresql://user:pass@ep-name-pooler.neon.tech/dbname?sslmode=require&channel_binding=require`.
   `server/db.ts` translates `sslmode` (which node-postgres ignores) into the driver's `ssl` option and
   strips the libpq-only parameters, so paste the string as it comes. `DB_SSL` / `DB_SSL_VERIFY` override
   it, `DB_POOL_MAX` sizes the pool (default 5), `DB_CONNECT_ATTEMPTS` how long to retry at boot (default 5).
2. If the database is unreachable at boot the process logs the reason and exits instead of serving
   fake data. To go back to the demo, unset `DATABASE_URL`.
3. The schema is created by `SCHEMA` in `server/db.ts` — no Flyway, no SQL files to run. It is
   `create table if not exists` plus two column widenings, so restarting against an existing database
   is safe and re-seeding does not happen (only an empty `products` + `categories` pair triggers the seed).
4. Images: `product_images.content` is a `bytea` column and `GET /api/v1/media/images/:id` serves it.
   Bytes go into the database, not onto disk, because Render recreates the container filesystem on every
   deploy. 5 MB per file, JPEG/PNG/WebP/GIF only.

Verify it end to end (drops the `public` schema of the target database, so point it at a scratch branch;
it refuses names that don't look like `test|scratch|demo|tmp` unless `E2E_ALLOW_DROP=1`):

```bash
DATABASE_URL=postgres://... PORT=3210 ADMIN_BOOTSTRAP_PASSWORD=... node scripts/e2e-postgres.mjs
```

46 checks: auth, upload byte-for-byte round-trip, checkout, a customer signing in as the phone that
ordered (profile write, saved address, and a second phone getting 404 on that order), then a **restart**
and re-read of the product, its image bytes, the order, its status, history, remaining stock and the
customer's own profile and address.

The customer side has its own suite, and it needs no database:

```bash
PORT=3216 node scripts/e2e-customer.mjs
```

43 checks: unguessable session token, the profile form really writing and reading back, sign-out keeping
the account, saved addresses, and a second customer being unable to read or cancel the first one's orders.

## Deploying to Render

`render.yaml` is the blueprint; `DATABASE_URL`, `ADMIN_BOOTSTRAP_PASSWORD` and `ALLOWED_ORIGINS` are
`sync: false`, i.e. Render asks for them once at creation and stores them as secrets. Create the service
from the blueprint (New -> Blueprint -> this repo) and paste:

| Variable | Value |
| --- | --- |
| `DATABASE_URL` | the Neon **pooled** connection string, unchanged |
| `ADMIN_BOOTSTRAP_PASSWORD` | your own 12+ character password; leave set only until first login, then change it in the panel |
| `ALLOWED_ORIGINS` | empty when the SPA is served by this service (the default); otherwise the exact site origin, e.g. `https://debol.pages.dev` |

`NODE_ENV=production`, `PORT=10000`, `NODE_VERSION=22` and the build/start commands are already in the
blueprint. `dist/` is built during the Render build (`npm run build`) and the `docs/api-samples` seed
files ship in the repo, and no `.env` or secret file is read from disk — `server.ts` only looks at the
environment. The [Dockerfile](Dockerfile) is the alternative path (`runtime: docker`); `.dockerignore`
keeps `.env`, `.env.*`, `node_modules`, `dist` and `data/uploads` out of the image.

Two constraints to keep on Render:

- **Run exactly one instance, one web service.** `server/persist.ts` writes the whole in-process state
  back on every mutation, so a second instance (or a scale-up) would overwrite the other's edits. Set
  the plan's instance count to 1 and do not add background workers that mutate the same tables.
- **Free plan sleeps.** The service cold-starts on the first request after idle; the boot retry loop
  (`DB_CONNECT_ATTEMPTS`, default 5 with backoff) is what carries it through Neon accepting connections
  late. Writes are flushed on `SIGTERM`, so a deploy does not lose the last mutation.

### If the build fails with TS7016 on `pg` or `busboy`

`npm run build` runs `tsc --noEmit`, so it needs type declarations, and Render's installer does not
always build `devDependencies` (a first deploy failed exactly that way). Every package the build reads -
`typescript`, `vite`, `tsx`, all of the `@types/*` - therefore lives in **`dependencies`**, which is why
`devDependencies` is absent from `package.json`. Keep it that way when adding a dependency: a build-only
type package in `devDependencies` is a deploy failure waiting to happen. If a service was created as a
plain Web Service rather than from `render.yaml`, check its dashboard build command is
`npm install && npm run build` and that `NODE_ENV` is set to `production`.

## Logging in as admin

Go to `/admin/login` with one of the seeded owner addresses (`owner@kidsstore.test` or
`demo@kidsstore.test`) and the value of `ADMIN_BOOTSTRAP_PASSWORD`. At boot that password is scrypt-hashed
onto every active `OWNER` row that has no hash yet - the captured `admin_administrators.json` carries no
credentials, so this is what makes a fresh database signable. Set a per-account password afterwards with
`POST /api/v1/admin/administrators/:id/password` (12+ characters) and drop the env variable.

`POST /api/v1/admin/auth/login` returns a random 48-hex token backed by an `admin_sessions` row (12-hour
TTL) when a database is configured, and an in-process session otherwise. Every other `/admin/**` route is
gated by a router-level middleware that resolves that token: no token or an unknown one is `401`, an
inactive account is `403`. `/admin/auth/dev-login` answers `404` unless `ADMIN_DEV_LOGIN=true` and
`NODE_ENV` is not `production`; no page in the frontend calls it. The password never appears in a response:
`GET/POST/PUT /admin/administrators*` map the row through `publicAdmin()`, which replaces the hash with a
`hasPassword` boolean.

## Not implemented / deviations

Read this before demoing or deploying.

1. **No separate `bot/` module (deliberate architectural deviation).** The build brief asked for a
   top-level `bot/` service. The Telegram bot lives in the backend at
   `backend/src/main/kotlin/com/kidsstore/telegram` instead, so that notification enqueueing joins the
   *same* database transaction as the order/state change (`NotificationService` is `@Transactional` and
   is called from inside `CartAndCheckout` / `OrderStatusService`), and so inline button callbacks run
   through the same `OrderStatusService` state machine and admin-pairing check as the panel. Do not
   look for, or document, a standalone bot service.
2. **Only the local storage driver exists.** `STORAGE_DRIVER` is bound in `application.yml` and
   `AppProperties.Storage`, but no code reads it: `StorageService` always writes to
   `STORAGE_LOCAL_DIR`, and `WebConfig` always maps `STORAGE_PUBLIC_BASE_URL` to that directory.
   Setting `STORAGE_DRIVER=s3` changes nothing. An S3/Spaces driver is a comment in `StorageService`.
3. **Some env vars are configured but not read.** `TELEGRAM_PAIRING_TTL_MINUTES` (pairing expiry is
   hardcoded to `plusMinutes(15)` in `TelegramPairingService.issueCode`), `TELEGRAM_MAX_ATTEMPTS`
   (outbox rows get `maxAttempts = 8` in `NotificationService`), `CURRENCY_LABEL` (currency comes from
   `store_settings.currency`) and `STORAGE_DRIVER` (above). `TELEGRAM_DISPATCH_INTERVAL_MS` does work,
   through the `@Scheduled` placeholder. Changing the other four has no effect today.
4. **Dev-auth guard is profile-name based.** `SecurityConfig.devAuthGuard` only refuses startup when an
   *active profile* is literally `prod` or `production`. Deployments that use other profile names must
   keep `DEV_AUTH_ENABLED=false` themselves.
5. **Test coverage is backend-only.** `./gradlew --offline test` runs 65 JUnit 5 tests over 9 classes
   against the real `kidsstore_test` PostgreSQL database (phone validation, BigDecimal money rounding,
   initData HMAC verification, order state machine, cash-collection gating, oversell/lock behaviour,
   idempotency, admin role authorization, outbox retry, age-group catalog filtering). The frontend has no test script
   (`package.json` defines `dev`, `build`, `preview`, `typecheck`); UI correctness is checked by hand in
   a browser plus `scripts/acceptance.mjs` ([docs/ACCEPTANCE.md](docs/ACCEPTANCE.md)).
6. **Cash on delivery only.** `orders.payment_method` has a `CHECK (... = 'CASH_ON_DELIVERY')`
   constraint, and checkout rejects anything else with `payment_method_unavailable`. No gateway, no
   refunds (`REFUNDED` is an allowed `payment_status` value but no endpoint sets it).
7. **Rate limiting is in-process and keyed on `request.remoteAddr`** (`RateLimiter`, fixed 1-minute
   windows, cleared when >5000 buckets). Behind a reverse proxy every request shares the proxy IP,
   which will trip limits early; the limiter is also not shared between instances.
8. **The backend does not serve the SPA.** `WebConfig` only maps `/api/v1/media/**`. `GET /` and
   client-side routes must be handled by the static host / reverse proxy
   ([docs/DEPLOYMENT.md](docs/DEPLOYMENT.md)).
9. **No `.env` loader.** There is no dotenv dependency in `build.gradle.kts`; Spring reads the
   environment. Root `.env.example` is documentation: export the values (`set -a; source .env; set +a`)
   or set them in the platform.
10. **Containers exist, CI does not.** `backend/Dockerfile` and `render.yaml` are new (section 10 of
    [docs/DEPLOYMENT.md](docs/DEPLOYMENT.md)) and have never been built or deployed from this machine -
    Docker is not installed here. There is still no compose file and no pipeline config.
11. **Flyway + PostgreSQL 18.** The recorded startup log shows
    `Flyway upgrade recommended: PostgreSQL 18.6 is newer than this version of Flyway and support has
    not been tested` (it still applied V1-V4 successfully). `render.yaml` therefore pins PostgreSQL 17.
12. **Everything is English-only.** The catalog language columns, the API fields and the UI strings all
    went in V3 plus the frontend language removal, so Telegram notification bodies, the `message` field
    of the error envelope, and order-history notes (e.g. `Order placed by customer`) are consistent with
    the screens. Enum *values* are translated in the frontend through the `status.*` keys; free text from
    the API is shown as it arrives.
13. **The admin notification list titles event types with `titleCase()`** (`NEW_ORDER` -> "New Order")
    instead of locale keys, as does the audit page for actions and actor types.
14. **One JS bundle.** `vite build` emits a single 773.57 kB chunk (226.89 kB gzip); routes are not
    lazily imported yet, so the admin panel ships with the storefront.
15. **The write-back is whole-state and single-instance.** `persistAll()` re-upserts every row after each
    mutating response instead of diffing, which is fine for a few dozen products but means two Render
    instances would overwrite each other. Run **one instance**. Scaling past that means moving the
    handlers onto SQL per request rather than keeping `server/data.ts` as the working set.
16. **A write lands after the response.** `schedulePersist()` is queued on the response `finish` event and
    serialised through a promise chain, so a crash in that window loses the last mutation, and a failed
    write is logged (`[db] persist failed:`) without turning a good response into a 500. `SIGTERM`/`SIGINT`
    flush the queue before exiting, which covers Render's deploy restarts.
17. **`ADMIN_BOOTSTRAP_PASSWORD` applies to every owner that has no hash.** The seed has two `OWNER` rows,
    so both start with the same password. Set a per-account password from the panel and remove the
    variable. Non-owner roles are never bootstrapped; they stay sign-in-disabled until an owner sets
    their password.
18. **The sample catalogue has zero product images.** `docs/api-samples/*.json` contains no `images` rows
    (verified: 21 products, 0 images), so the seeded storefront renders the `images.length > 0 ? images :
    [null]` placeholder in `ProductPage.tsx`. Photographs are added per product from the admin editor,
    which is what the upload endpoint exists for. Nothing here invents imagery.
19. **Order line ids are derived, not stable across data edits.** `order_items.id` is written as
    `order_id * 1000 + index` on each save (the seeded items all arrived with `id: 1`, so they could not be
    reused), and `order_history` rows are deleted and re-inserted. Nothing in the API keys off those ids.
20. **The `_am` columns are vestigial.** `name_am` / `description_am` / `title_am` / `body_am` are still in
    the schema because `Product.nameAm` and `Category.nameAm` are still in the row types, but the only code
    that ever writes them is `POST /admin/products`, no DTO returns them and no page in `src/` references
    them - so they stay `NULL`. `docs/DATA-AND-MIGRATIONS.md` records V3 removing Amharic from the product
    surface; the app is English-only.

## Conventions worth knowing before editing

- Entities are written with `open var` on every property: the `kotlin-spring`/`allopen` plugin is not
  resolvable on the build network, so `open` is explicit (`build.gradle.kts` comment). Kotlin classes
  that Spring must proxy have to stay `open`.
- Plugins are applied through `buildscript` + `apply(plugin = ...)` rather than the `plugins {}` DSL,
  because the Gradle plugin portal is unreachable from the development network; dependencies come from
  Maven Central.
- Errors are uniform: `{"error": "<code>", "message": "...", "fields": [...], "requestId": "..."}` via
  `ApiExceptionHandler`. Never add a stack trace or DB detail to a response.
- Frontend design/toolchain rules (Tailwind v3 palette, `Price`/`money()` only, strict tsconfig with
  `noUnusedLocals`) are in `docs/PAGE_BRIEF.md`.
